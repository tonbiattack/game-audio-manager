# 常駐アプリとしての負荷計測

計測日: 2026-11-25 / Windows 11 build 26300 / .NET 10 / WPF + WPF UI 4.3.0

対象 Issue: #44

## 計測方法

`Get-Process` の `TotalProcessorTime` と `WorkingSet64` を一定間隔で取得し、
差分から平均 CPU 使用率（1 コア基準）を求める。

- 監視間隔: 既定 5 秒
- ルール: 1 件（chrome、自動適用 ON）
- 計測中の操作: なし（アイドル）

## 結果

### ウィンドウ表示中（60 秒）

| 項目 | 値 |
| --- | --- |
| 平均 CPU | **2.1 %**（1 コア基準） |
| ワーキングセット | 276 MB → 271 MB |
| スレッド数 | 108 |
| ハンドル数 | 658 |

### トレイ常駐（ウィンドウ非表示、60 秒）

| 項目 | 値 |
| --- | --- |
| 平均 CPU | **2.03 %** |
| ワーキングセット | 273 MB → 269 MB |

ウィンドウを隠しても CPU・メモリはほぼ変わらない。WPF のビジュアルツリーは
`Hide()` では破棄されないため、常駐中のフットプリントはこの値が基準になる。

### 最適化後（トレイ常駐、60 秒）

起動していないアプリのセッション列挙をやめた後の値。

| 項目 | 値 |
| --- | --- |
| 平均 CPU | **1.88 %** |
| ワーキングセット | 261 MB → 266 MB |

## 評価

- **CPU は許容範囲**。ただし 1 コアの約 2% は、常時稼働のユーティリティとしては
  やや重い部類。主な内訳は 5 秒ごとの再生エンドポイント列挙（COM）とセッション照会。
- **メモリ約 260 MB は重い**。WPF と WPF UI のベースラインが大半で、
  アプリ側のデータ構造（数十件の一覧）はほぼ寄与していない。
  削るには `Hide()` ではなくウィンドウのビジュアルツリーを破棄して再生成する設計変更が必要で、
  起動のたびの再構築コストと引き換えになる。

## 実施した最適化

`WatcherService.BuildStatuses` で、**起動していないプロセスのセッション列挙をスキップ**した。

- 変更前: 全ルールについて毎サイクル全エンドポイント×全セッションを走査
- 変更後: 起動中のプロセスのみ照会
- 効果: CPU 2.03 % → 1.88 %、メモリ 269 MB → 266 MB（この環境・このルール数での実測）

登録ゲームが増えるほど効果は大きい。起動していないゲームが多い構成ほど差が出る。

## 調整手段

- `settings.json` の `watchIntervalSeconds` で監視間隔を変更できる（1〜3600 秒）
- 10 秒にすると COM 呼び出し回数が半分になり、CPU も概ね半減する見込み
  （**未計測**。計測する場合はこの表に追記すること）
- ルールが 0 件の場合、監視は起動しない（設定で自動開始がオフかつルールなしのとき）

## 未計測

- 監視間隔を変えた場合の比較（5 秒 / 10 秒 / 30 秒）
- ルール 10 件・うち 3 件起動中のケース
- スリープ復帰直後やデバイス抜き差し直後の一時的なスパイク
- 長時間（数時間）稼働時のメモリ増加（リーク有無）

いずれも「計測していない」であり、問題がないという意味ではない。

## 参考: イベント駆動について

`WM_DEVICECHANGE` と `PowerModeChanged` で即時再評価しますが、
**アプリの起動検出はイベントでは拾えない**ため低頻度ポーリングを併用しています。
`IMMNotificationClient` はエンドポイント単位の変更をより正確に拾えますが、
.NET での COM コールバック実装（`ComWrappers`）が必要なため、
現行方式で問題が出た場合の選択肢として保留しています（#44 の方針）。
